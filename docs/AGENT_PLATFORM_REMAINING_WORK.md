# Remaining work against the agent execution platform plan

Audit: 4 October 2026. Source: `Open Learn 2.0/26_agent_execution_platform.md`, especially sections 6–8, 16, 18 and 21–22. Compared the current implementation and milestone evidence; this is a code/document inspection, not a new full regression run. Milestone 7 is being built by another agent and is not reassigned here. Its mobile/hosting files are in progress; file presence is not release acceptance.

## Conclusion

Slices 1–6 provide useful durable capability modules, but they do not yet deliver the complete general-purpose conversational assistant described by the plan. The largest missing layer is shared conversational admission plus a bounded model/tool kernel and cross-capability orchestration. Completing hosting and native mobile in milestone 7 does not automatically fill that gap.

## Scope distinctions

Section 16 defines the selected release. Full GUI desktop automation, realtime spoken conversation, screen sharing, additional providers, shared multi-user workspaces, public skills marketplace and unattended external writes are explicitly excluded. They should not be treated as missing prerequisites. Standing authorization structures are intentionally disabled. Broader announcement/deadline webhook triggers and sophisticated proactive weak-concept relevance are future extensions beyond the first weekly/finalized-lecture responsibility unless that release scope is expanded. A changed-deadline journey still needs existing academic reconciliation wired into coordinator/action orchestration.

## Documentation discrepancies to reconcile

- Initial status/critique and older foundation/research records still describe capabilities as unbuilt that later slices or live adapter tests delivered. Use dated implementation records and current code as evidence.
- Plan proposes 30-minute approval expiry; milestone 6 implements 15 minutes. Decide/configure the policy and align UI, implementation and brief.
- Plan calls for a shared model/tool kernel and general conversation path; milestone completion statements currently describe bounded capability slices, not that integration layer.
- Plan proposes SourceMemory-backed operational context; current responsibility notes use separate additive tables. Decide the authoritative context integration while retaining owner/correction/delete behavior.
- Exact research claim support and general-format output verification cannot be inferred from citation existence, process exit success or accepted child object hashes.

1. Unified admission and shared bounded kernel, including generic input/dependency contracts.
2. Execution context/memory and general analysis/output verification.
3. Cross-capability learner/app/child workflows and browser recovery.
4. Priced budgets, retention and operator recovery/observability, coordinated with milestone 7.
5. Full integrated release acceptance against real providers, hosted storage/runtime and physical devices; update the plan status against actual evidence.

Milestone 7 can continue in parallel, but the final product needs these integration packages as well as its mobile/deployment work.

## Detailed live and hosted implementation handoff

The following packages expand the acceptance gaps into executable engineering work. Implement missing code first with deterministic tests, then run controlled integration and live acceptance. Credentials, production policy, signed builds and physical devices are inputs, not facts an agent can invent. A configured variable or successful provider hello-world is not proof of a complete user journey. Record each package as `code_pending`, `local_verified`, `live_blocked`, `live_verified`, or `release_accepted`, with the actual evidence and remaining reason. These labels belong in the release evidence record; they do not require a new product task-state enum.

### Shared execution rules for the receiving agent

Read this file, the authoritative brief, `docs/CURRENT_ARCHITECTURE.md`, the relevant milestone records and current repository instructions. Reinspect shared files and migration heads before editing: milestone 7 and other work may have advanced since this audit. Preserve other agents' changes and retain one claim owner for each job kind. Use the intended backend environment and locked web/mobile dependencies; do not assume a global Python installation matches the repository environment.

Use disposable owner identities, conversations, provider resources and test storage. Name each live run with a unique non-secret acceptance ID and persist its resource manifest before external creation. Tests must not delete user data or reset production buckets/databases. Keep paid/live suites opt-in with a per-run ceiling, maximum calls/resources, timeouts and a guaranteed cleanup path. A live-write test needs an explicitly designated test account, destination/calendar and allowed action: authorization to implement code is not authorization to send a real email or modify a real calendar. Prepare fixtures, tests and diagnostics while those inputs are missing. Do not put credentials, OAuth codes, cookies, human-control URLs or private message bodies in evidence logs.

Use deterministic fault injection at named boundaries: before dispatch, after provider acceptance, after object storage, before database commit and after lease expiry. Expose hooks only through injected adapters or test-only harnesses, never unauthenticated production crash endpoints. Live tests may exercise real providers with controlled faults in the client response/worker boundary; do not pretend an arbitrary mocked provider acceptance proves a real provider effect. Every harness must close clients and record cleanup success, deferred retry or an actionable orphan obligation.

Proposed additions below are files to build, not commands or tools that already exist. A sensible layout is `backend/tests/integration/` for disposable hosted tests and `backend/scripts/` for bounded acceptance runners. Match the existing test conventions rather than introducing a competing framework. At completion, document exact runnable commands and required variable names in a release guide. ### A. Live Google workflows

**Expected learner experience.** The learner chooses a Google account and specific permissions, inspects permitted Drive/Gmail sources, imports a supported file, then reviews an exact email or Calendar change. Approval applies to that account and payload only. Disconnecting stops new dispatch. A lost response shows uncertainty and offers a provider-evidence check; it does not offer a disguised resend. A provider receipt proves API acceptance, not that someone read or received the email.

**Reuse and missing work.** Extend `google_connector.py`, `connector_intake.py`, `connected_actions.py`, `connected_routes.py` and `connected-task-panel.tsx`; use the mobile action review built by milestone 7. Preserve encrypted tokens, owner-bound single-use PKCE state, revision fencing and durable operation records. Add the coordinator adapters described earlier so source retrieval can lead to a draft without manually copying values between forms. Add bounded Calendar listing/range reads and a source-pagination interface with explicit incomplete coverage. Any new capability must request only its required scopes and disclose them before consent. Validate paginated result schemas and provider payload bounds. If provider-side grant revocation is added, persist its outcome and distinguish local disconnection, attempted provider revocation and confirmed provider revocation; local token deletion alone cannot prove the Google grant is gone.

**Prerequisites.** A Google OAuth web client, exact backend callback URL, enabled APIs, approved/test-user access for the selected scopes, encrypted token-vault key, hosted identity and a designated test Google account. Supply these through server secret configuration. `OPENLEARN_GOOGLE_CLIENT_ID`, `OPENLEARN_GOOGLE_CLIENT_SECRET`, `OPENLEARN_GOOGLE_REDIRECT_URI` and `OPENLEARN_CONNECTOR_VAULT_KEY` already exist. Do not publish the vault key or put provider secrets in Vercel public variables. Verify the current Google documentation and account-consent requirements when implementing; do not infer readiness from scope strings alone.

**Acceptance sequence.**

1. Sign in as test owner A and authorize only a selected read capability. Finish real OAuth and verify the account identity and actual granted capabilities in the UI. Reuse the callback state, alter it, expire it and submit it under an inappropriate context: no new connection may be created. Check callback redaction at both application and ingress logs.
2. List more than one page of synthetic Drive files and Gmail messages. Inspect a selected message as untrusted text. Import a known PDF/plain-text/Markdown file, compare SHA-256, verify existing material/version ownership, and retry with the same intake key. Changed content under the old key must not silently replace the material. Reject unsupported or oversized content before publication.
3. Prepare an email to an explicitly approved test inbox with a harmless acceptance ID and owned artifact attachment. Verify exact account, recipients, body, attachment manifest, expiry and content hash in both web and native review. Reject one draft and prove no provider call. Approve a second and prove one durable operation and provider message reference despite duplicate decision submission or page reload.
4. Create a synthetic Calendar event in a dedicated test calendar, then prepare an update. Change the event independently after review: stale ETag must prevent overwriting that edit and require a fresh review. Exercise timezone and attendee/notification fields, including daylight-saving boundaries, without inviting unrelated people. Repeat approval delivery and confirm no duplicate create.
5. After actual provider acceptance, interrupt result recording once. Recover the worker and reconcile using the stable message/event markers. Confirm one effect. For Gmail without read permission, or when evidence is unavailable, retain `outcome_unknown` with no resend. Inject read failures without turning an uncertain action into a false definitive failure.
6. Disconnect/revoke permission before queued dispatch, during refresh and during an already in-flight call. Queued/new calls must stop; an effect already accepted may remain and must be reported. Owner B cannot inspect A's connections, messages, drafts, operation receipts or attachments. Remove test events through an explicitly scoped cleanup action; document whether test mail is retained rather than silently adding mail-deletion authority.

**Required evidence.** Sanitized scope/account metadata, task/draft/operation IDs, provider references, counts of actual write effects, hash comparison, stale-version rejection, revocation timing, unknown-outcome behavior and cleanup manifest. Add a bounded runner such as `agent_google_acceptance.py`; OAuth must use a human-authorized test login rather than passwords scripted into the harness. Done means all supported real workflows pass, not merely OAuth succeeds.

### B. Full live research

**Expected learner experience.** A learner asks a real research question, sees the sources actually inspected, receives readable source-linked files with honest limitations, and can return after a worker or client restart. Source inspection and download remain owned and governed by retention. A sourced partial result must not become a fully verified claim or learner mastery.

**Reuse and missing work.** Reuse `research.py`, `research_sources.py`, `research_contracts.py`, WebEvidenceService/Exa, artifact publication and the existing model provider. Existing live Exa search/open evidence is valuable but covers the adapter only. Add an end-to-end runner exercising authenticated admission, supervised workers, retained sources and downloads. Preserve provider receipts across restart. For full claim-support quality, add bounded claim-level evidence checking and disagreement/coverage reporting with pass/fail/unknown outcomes; a second model's agreement is not independent factual proof. Exact quotes, numeric claims and source accessibility need deterministic checks where possible. Retain partial semantics for unresolved claims. Use the existing learning owners to define whether an explicitly limited result may be taught; do not remove the verified-result continuation guard simply to make the test pass.

**Prerequisites.** Existing Exa configuration, a selected compatible synthesis model if synthesis is enabled, per-run search/model limits, retention policy and permitted public questions. Use controlled attached materials for exact factual checks plus a small live public-source case. Record model/provider/schema versions without recording secrets. **Acceptance sequence.**

1. Admit attached-only, external-only and attached-preferred research through the real API as A. Check source policy, source counts, inspected coverage, generated Markdown/JSON parsing, claim-to-source references and provenance. An unavailable external provider produces the documented partial/setup outcome rather than fabricated citations.
2. Restart after successful retrieval and before synthesis/publication. Confirm the same revision reuses durable receipts and does not repeat completed provider calls merely because short-lived response caches expire. Check that a real worker continues when the browser closes.
3. Expire/delete a retained source and detach or change a material version at retrieval, synthesis, object-write and pre-publication boundaries. No stale report may be newly published, and dependent downloads must no longer bypass source access. Exercise owner B with guessed source/artifact identifiers.
4. Supply prompt-injection text and invented citation requests inside controlled source content. The system must treat it as evidence text, reject unauthorized tools/generated references and preserve source policy. Test contradicting sources and unsupported conclusions: output must retain the disagreement or an unknown check.
5. Test rate-limit/provider timeout, cancellation and steering during retrieval or synthesis. Account/provider quota failures must be explicit. New constraints create the appropriate input revision and fence stale publication.
6. Exercise the full research → learner explanation → quiz → learner-answer journey after its integration is built. Report format/citation/semantic verification and learning delivery separately; only the learner's valid assessed response may create performance evidence.

**Required evidence.** Reproducible question/material fixture, actual inspected sources and bounded excerpts, provider-call counts, result hashes, parser checks, claim-check results, restart receipts and authenticated source/download denial. Record task success, factual support and learning outcome separately. Add a runner such as `agent_research_acceptance.py` and mark real-source variability explicitly.

### E. PostgreSQL concurrency, migrations and restart recovery

**Expected system behavior.** Separate API/worker processes can admit, answer, claim, approve and reserve concurrently without duplicate work or stale commits. Database locks/CAS enforce authority; an in-process mutex is insufficient for hosted correctness. Provider/object calls remain outside short transactions.

**Reuse and missing work.** Use existing `database.py`, WorkflowStore, execution outboxes, agent repository and migration graph. Inspect session → task → job and connection/action/budget lock ordering against every new path. Add real PostgreSQL tests with independent connections and spawned worker processes, barriers and deterministic fault injection. Parameterize test-store construction rather than attempting to point SQLite-file fixtures at a PostgreSQL URL. Check rollback of reservations as well as exceptions. Fix actual deadlocks/lost updates through consistent lock order and bounded safe transaction retry; never automatically retry an external effect because its database transaction failed.

**Prerequisites.** A disposable PostgreSQL database/schema identified explicitly as acceptance-only, supported driver, intended server version, TLS/credentials and migration permissions. Seed both old-application and current schemas using test fixtures. Keep schema reset confined to the verified test target. Apply one migration release job; do not race startup migrations on production replicas.

**Required test matrix.**

| Concurrent boundary | Required invariant |
| --- | --- |
| Duplicate admissions/commands from two API processes | One logical message/task/command; conflicting content rejected |
| Two workers claiming the same job | One current lease; old worker cannot publish after lease loss |
| Input correction versus execution/publication | Acknowledged revision fences old result; immutable old completed version remains recoverable |
| Two approvals/decision retries | One queued operation; one dispatch claim; payload/hash/account binding retained |
| Approval/refresh versus disconnect/account deletion | Queued work stops; refresh cannot resurrect revoked connection; in-flight effects remain accurately uncertain/confirmed |
| Concurrent child admissions and charges | Child and shared limits never go below zero; duplicate charge identity settles once |
| Scheduler scans on multiple workers | One occurrence/outbox obligation; DST/missed/overlap policy maintained |
| Object published after cleanup/cancellation | Late upload remains tracked and reaped; no stale final artifact |
| Worker/process termination at dispatch boundaries | Checkpoints/receipts recover; unknown writes reconcile rather than replay |

**Migration and restore sequence.** Upgrade a representative pre-agent database with existing browser/learning IDs. Verify each legacy handler still owns its tasks. Exercise the concurrent branch merge and latest migrations without assuming a hardcoded head. On a disposable database, rehearse an explicit downgrade only where supported, then roll forward; relative downgrade across a merge can be ambiguous. Test a compatible forward repair and rollout with fenced/drained new-schema jobs. Restore database and object fixtures together, then run a reconciliation pass before workers resume. Record transaction isolation, lock waits, deadlocks, expected retry counts and final row/event counts.

**Required evidence.** Exact PostgreSQL/driver/migration versions, process count, deterministic race schedule, invariant assertions and queryable receipts. Repeated single-process SQLite success cannot substitute. Build a suite such as `test_agent_postgres_integration.py` with explicit environment opt-in and no default production connection.

### F. Private S3 lifecycle and artifact durability

**Expected learner experience.** Files and recordings are durable across API/worker restarts, remain private, match their original hashes and can be exported/deleted according to policy. A database row cannot claim publication of missing bytes. Cleanup does not silently destroy the only durable output or claim physical erasure before it completes.

**Reuse and missing work.** Reuse `object_store.py`, browser evidence objects, agent artifacts, lecture object adapters, identity object manifests and cleanup obligations. Material, assistant-artifact and recording adapters must be inventoried: sharing a bucket does not prove they use the same key policy or deletion behavior. Reuse current immutable conditional writes; test provider compatibility and concurrent identical/different payloads. Do not treat an ETag as the application's SHA-256. Verify application-recorded hashes on reads. Keep private access through authenticated APIs or tightly bounded authorized URLs whose expiration/revocation semantics are explicit.

**Prerequisites.** A dedicated acceptance bucket/prefix, region/endpoint, least-privilege application role and credentials through server secrets. Configure both `OPENLEARN_OBJECT_BUCKET` and `OPENLEARN_ASSISTANT_S3_BUCKET` as required by the actual adapters. Inventory encryption, public-access policy, versioning, multipart lifecycle, replication and backups. Existing `S3ObjectStore.delete` issues a normal object delete; if versioning is enabled, a delete marker may leave older versions. Define and implement privacy erasure/retention for retained versions separately instead of promising physical deletion from the current call.

**Acceptance sequence.**

1. Upload known material, lecture segments, retained source content and task outputs as A. Read through each adapter/API and verify hashes, sizes and content type. Restart workers/API and read again without local filesystem state. Anonymous and B requests must be denied even if the key is guessed.
2. Concurrently put identical bytes under one key: idempotent success. Put different bytes under that key: immutable conflict. Test the configured S3-compatible provider's actual conditional-write behavior. Corrupt/mismatch a controlled object or metadata fixture and ensure publication/download fails closed.
3. Interrupt between prepared metadata, upload and final publication. Recover once without duplicating objects/results. Cancel/delete during upload and exercise late-upload cleanup. Simulate denied writes, read timeout, missing object and delete failure; record retryable cleanup rather than losing the manifest.
4. Delete/expire a source and confirm dependent report access is invalidated. Delete an artifact/account and verify immediate API denial plus asynchronous storage cleanup.
